# Практическая работа №6. Смарт-контракт для управления состоянием доставки

Смарт-контракт [`DeliveryManager.sol`](DeliveryManager.sol) на **Solidity**
моделирует часть процесса доставки в **АС сервиса доставки** (BootcampLabs):
регистрацию доставки, назначение курьера, начало и завершение доставки,
отмену. Контракт хранит данные доставки, разрешает только допустимые
переходы между статусами и проверяет, **кто** вызывает операцию. Каждое
изменение фиксируется событием. Работа выполнена в **Remix IDE**.

Контракт **не заменяет backend**. Клиенты, товары, адреса и сами заказы
остаются в backend (как Order Service в ПР №5). В blockchain вынесена
только небольшая часть логики, для которой важны неизменяемая история
и контроль действий: статус доставки, назначенный курьер и кто и когда
менял статус.

Где контракт находится в общей системе (в работе реализован только он,
остальное показано для понимания):

```
   Пользователь (клиент / оператор / курьер)
            │ вход по логину и паролю
            ▼
  ┌────────────────────┐   токен (JWT) с ролями   ┌──────────────────────┐
  │   Keycloak (IAM)   │ ───────────────────────► │ Front-end АС сервиса │
  │ realm brave_turtle │                          │      доставки        │
  └────────────────────┘                          └─────┬──────────┬─────┘
                                                        │ REST     │ транзакции,
                                                        ▼          ▼ подписанные ключом
                                          ┌──────────────────┐  ┌───────────────────────┐
                                          │     Backend      │  │  DeliveryManager.sol  │
                                          │ заказы, клиенты, │  │ статус доставки,      │
                                          │ товары, адреса   │  │ курьер, роли,         │
                                          │ (PostgreSQL)     │  │ история (события)     │
                                          └──────────────────┘  └───────────────────────┘
                                                 orderId ────────────► orderId
```

## 1. Используемые технологии (подробно)

### Блокчейн и Ethereum

**Блокчейн** — распределённая база данных из цепочки блоков. Каждый блок
содержит транзакции и хэш предыдущего блока, поэтому изменить старую
запись незаметно нельзя: изменится хэш, и цепочка «порвётся». Копия данных
хранится у всех узлов сети, единого владельца у базы нет.

**Ethereum** — блокчейн, в котором кроме переводов денег можно хранить
и выполнять программы — **смарт-контракты**. Состояние контракта (его
переменные) хранится в блокчейне. Изменить его можно только транзакцией,
которая вызывает функцию контракта и проходит все проверки, записанные
в коде. Поэтому правила («нельзя перевести из Created в Delivered»)
нельзя обойти: их проверяет не сервер, который можно взломать или
переписать, а каждый узел сети.

### Смарт-контракт и EVM

**Смарт-контракт** — программа, развёрнутая в блокчейне по своему адресу.
После деплоя код контракта изменить нельзя. **EVM** (Ethereum Virtual
Machine) — виртуальная машина, которая выполняет байткод контракта на
каждом узле. Solidity компилируется в этот байткод, примерно как Java
компилируется в байткод JVM.

### Solidity 0.8.24

**Solidity** — язык смарт-контрактов для EVM, по синтаксису похож на
Java/JavaScript. Что из языка используется в контракте:

| Конструкция                        | Где в контракте                                       | Зачем                                                       |
| ---------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------- |
| `// SPDX-License-Identifier: MIT`  | первая строка                                         | лицензия кода; без неё компилятор выдаёт предупреждение     |
| `pragma solidity ^0.8.24;`         | вторая строка                                         | версия компилятора: 0.8.24 и новее в рамках 0.8.x            |
| `contract`                         | `DeliveryManager`                                     | аналог класса                                               |
| `enum`                             | `Status`, `Role`                                      | статусы доставки и роли. Хранятся как число `uint8` (0, 1, 2…) |
| `struct`                           | `Delivery`                                            | запись о доставке                                           |
| `mapping(K => V)`                  | `roles`, `deliveries`, `deliveryIdByOrderId`          | хэш-таблица. Для любого ключа есть значение по умолчанию (0, `address(0)`, первый элемент enum) |
| `address`                          | `customer`, `courier`, `admin`                        | адрес аккаунта (20 байт)                                    |
| `immutable`                        | `admin`                                               | задаётся один раз в конструкторе и больше не меняется       |
| `msg.sender`                       | все проверки ролей                                    | адрес того, кто вызвал функцию. Подделать его нельзя: транзакция подписана закрытым ключом этого аккаунта |
| `block.timestamp`                  | `createdAt`, `updatedAt`                              | время блока, в который попала транзакция                    |
| `modifier`                         | `onlyAdmin`, `onlyRole` и т. д.                       | повторяющиеся проверки перед телом функции (см. раздел 4.5) |
| `error` + `revert`                 | `InvalidStatusTransition` и др.                       | пользовательские ошибки с параметрами                       |
| `require`                          | `grantRole`                                           | проверка условия с текстом ошибки                           |
| `event` + `emit`                   | `DeliveryCreated` и др.                               | журнал изменений (логи)                                     |
| `storage` / `memory`               | `_setStatus`, `getDelivery`                           | `storage` — ссылка на данные в блокчейне, `memory` — временная копия на время вызова |
| `external` / `public` / `private`, `view` / `pure` | все функции                           | видимость и признак «только чтение» (см. ниже)              |

Видимость функций:

- `external` — функцию вызывают только снаружи (из транзакции или другого контракта);
- `public` — можно вызвать и снаружи, и изнутри контракта (`canTransition`
  вызывается из модификатора);
- `private` — только внутри контракта (`_setStatus`);
- `view` — функция только читает состояние, `pure` — даже не читает его
  (`canTransition` работает только со своими аргументами).

С версии 0.8 переполнение чисел проверяется автоматически: `++deliveriesCount`
не может «перескочить» через максимум, транзакция просто откатится.

### Remix IDE и Remix VM

**Remix IDE** (<https://remix.ethereum.org>) — среда разработки
смарт-контрактов, работает прямо в браузере, ничего устанавливать не нужно.
Используются три вкладки:

- **File Explorer** — файлы проекта;
- **Solidity Compiler** — компиляция и выбор версии компилятора;
- **Deploy & Run Transactions** — деплой и вызов функций контракта.

**Remix VM** — тестовый блокчейн, который работает внутри браузера.
В нём уже есть 10+ аккаунтов по 100 тестовых ETH. Блоки создаются сразу
при отправке транзакции, реальные деньги не тратятся. После перезагрузки
страницы всё состояние сбрасывается. Название в скобках, например
**Remix VM (Cancun)**, — версия правил EVM (хардфорк), которую он эмулирует.

### Транзакции и вызовы

С контрактом можно работать двумя способами.

| | Транзакция | Вызов (call) |
|---|---|---|
| Что делает | меняет состояние | только читает |
| Функции | `createDelivery`, `assignCourier`, `startDelivery`... | `getDelivery`, `statusName`, `roles`, `canTransition` |
| Кнопка в Remix | оранжевая | синяя |
| Попадает в блок | да, и остаётся в истории навсегда | нет |
| Стоит газ | да, платит отправитель | нет (если вызван не из транзакции) |
| Результат | статус «успех/откат» и события (logs) | возвращаемое значение |

### Газ

**Газ** — единица стоимости вычислений в EVM. Каждая операция стоит
определённое количество газа: сложение — 3, запись в новую ячейку
хранилища — около 22 100, базовая стоимость любой транзакции — 21 000.
Отправитель платит `газ × цена газа` в ETH. Так сеть защищается от
бесконечных циклов и спама. В Remix VM газ платится тестовым ETH.

Замеры газа по функциям контракта (в Remix цифры могут немного отличаться):

| Операция           | Газ (≈)   | Почему столько                                                  |
| ------------------ | --------: | --------------------------------------------------------------- |
| деплой             | 1 850 000 | в блокчейн записывается весь байткод контракта                  |
| `createDelivery`   |   210 000 | заполняется 7 новых ячеек структуры и запись в `deliveryIdByOrderId` |
| `assignCourier`    |    81 000 | новая ячейка `courier`, смена статуса, два события              |
| `grantRole`        |    47 000 | новая ячейка в `roles` и событие                                |
| `cancelDelivery`   |    54 000 | смена статуса и событие                                         |
| `startDelivery`    |    37 000 | смена статуса и событие (ячейки уже не пустые — это дешевле)    |
| `completeDelivery` |    37 000 | то же                                                           |

Отсюда видно, почему в блокчейн выносится только минимум данных: каждая
сохранённая ячейка стоит денег.

### События (events, логи)

`emit DeliveryStatusChanged(...)` записывает событие в журнал транзакции.
Сам контракт события прочитать не может, зато их читают front-end и backend:
подписываются на события или выбирают их по фильтру. Хранить их дешевле,
чем переменные. Параметры с `indexed` попадают в отдельные поля (topics),
по ним можно фильтровать: например, «все события доставки №1» или «все
доставки курьера X». По цепочке событий `DeliveryStatusChanged` можно
восстановить полную историю доставки: кто, когда и из какого статуса
в какой её переводил.

### require, revert и пользовательские ошибки

Если проверка не прошла, выполняется **revert**. Транзакция откатывается
целиком: все изменения в хранилище отменяются, события не сохраняются,
состояние контракта остаётся прежним. Ошибку видит тот, кто вызывал функцию.

- `require(условие, "текст")` — короткая форма: если условие ложно,
  делается revert с текстом. В контракте используется в `grantRole`.
- **Пользовательские ошибки** (`error InvalidStatusTransition(Status from, Status to)`)
  появились в Solidity 0.8.4. Они дешевле по газу, чем строки, и несут
  параметры: видно не только «что-то не так», но и из какого статуса
  в какой пытались перейти. Вызываются как
  `if (!условие) revert ИмяОшибки(параметры)`. Remix показывает их по имени
  и с параметрами. Это основной способ проверки в контракте.
- **Модификаторы** собирают такие проверки в одном месте, и функция
  подключает их в объявлении (см. раздел 4.5).

## 2. Связь с модулем «Доступы и front-end АС сервиса доставки» (BootcampLabs)

В модуле доступ к АС сервиса доставки настраивается через **Keycloak** —
систему управления доступом (IAM). В realm `brave_turtle_947` заведены:

- **clients** — приложения, которые подключаются к Keycloak:
  `account`, `account-console`, `admin-cli`, `broker`, `realm-management`,
  `security-admin-console`;
- **realm roles** — `platformauth_admin`, `platformauth_auditor`, а также
  стандартные `offline_access`, `uma_authorization`, `default-roles-…`;
- **client scopes** — какие данные попадают в токен. Например, scope
  `roles` добавляет в токен роли пользователя, по ним front-end решает,
  какие кнопки показать.

В Keycloak два шага: **аутентификация** (кто ты — логин и пароль,
в ответ выдаётся токен) и **авторизация** (что тебе можно — роли в токене).
В контракте эти шаги устроены так же, только средствами блокчейна:

| Понятие         | Keycloak / front-end BootcampLabs                       | Смарт-контракт                                                        |
| --------------- | ------------------------------------------------------- | --------------------------------------------------------------------- |
| Аутентификация  | логин и пароль → JWT-токен                              | подпись транзакции закрытым ключом → `msg.sender`                     |
| Хранение ролей  | realm roles, назначенные пользователю                   | `mapping(address => Role) roles`                                      |
| Администратор   | `platformauth_admin`, `security-admin-console`          | `admin` — тот, кто развернул контракт. Выдаёт роли через `grantRole` / `revokeRole` |
| Только чтение   | `platformauth_auditor`                                  | любой адрес: `getDelivery`, `statusName`, `roles`, события             |
| Проверка прав   | front-end скрывает кнопки, backend проверяет токен      | модификаторы `onlyAdmin`, `onlyRole`, `onlyAssignedCourier`           |
| Журнал действий | события Keycloak и логи backend                         | события контракта, которые нельзя изменить или удалить                |

Роли **Operator** и **Courier** — роли предметной области сервиса доставки
(оператор принимает заказ в доставку, курьер везёт). Роль **Customer**
отдельно не выдаётся: клиент определяется по полю `customer` в записи
доставки. Так клиент может отменить только **свою** доставку.

Что где хранится:

| В backend (как в ПР №5)                                     | В контракте                                        |
| ----------------------------------------------------------- | -------------------------------------------------- |
| ФИО, телефон и адрес клиента, состав заказа, товары, цены товаров | `orderId` — ссылка на заказ в backend          |
| учётные записи, пароли (Keycloak)                           | адреса аккаунтов и их роли                         |
| —                                                           | статус доставки, курьер, стоимость доставки, время, история изменений |

Персональные данные в контракт не попадают **намеренно**: всё содержимое
блокчейна публично (см. вопросы в разделе 9).

## 4. Устройство контракта

### 4.1. Данные доставки

```solidity
struct Delivery {
    uint256 deliveryId;  // номер доставки в контракте: 1, 2, 3...
    uint256 orderId;     // id заказа в backend BootcampLabs
    address customer;    // клиент
    address courier;     // назначенный курьер (0x000…0, пока не назначен)
    uint256 price;       // стоимость доставки в копейках
    Status  status;      // текущий статус
    uint256 createdAt;   // время создания (block.timestamp, секунды Unix)
    uint256 updatedAt;   // время последнего изменения
}
```

Переменные состояния:

| Переменная            | Тип                              | Назначение                                        |
| --------------------- | -------------------------------- | ------------------------------------------------- |
| `admin`               | `address immutable`, public      | администратор (кто развернул контракт)            |
| `deliveriesCount`     | `uint256`, public                | сколько доставок создано; он же последний номер   |
| `roles`               | `mapping(address => Role)`, public | роль каждого адреса                             |
| `deliveries`          | `mapping(uint256 => Delivery)`, private | сами доставки. Читаются через `getDelivery` |
| `deliveryIdByOrderId` | `mapping(uint256 => uint256)`, public | номер доставки по id заказа: защита от повторной регистрации |

Нумерация доставок начинается с **1**. Значение `0` в `mapping` означает
«нет записи», поэтому `deliveryIdByOrderId[orderId] == 0` значит, что
заказ ещё не регистрировался.

Цена хранится целым числом в копейках (`35000` = 350 ₽): дробных чисел
в Solidity нет.

### 4.2. Роли

```solidity
enum Role { None, Operator, Courier }   // 0, 1, 2
```

| Роль         | Как получить                                                  | Что может                                                   |
| ------------ | ------------------------------------------------------------- | ----------------------------------------------------------- |
| **Admin**    | развернуть контракт (`admin = msg.sender` в конструкторе)     | выдавать и отзывать роли: `grantRole`, `revokeRole`         |
| **Operator** | `grantRole(адрес, 1)`. Admin получает её автоматически в конструкторе | `createDelivery`, `assignCourier`, `cancelDelivery`  |
| **Courier**  | `grantRole(адрес, 2)`                                         | `startDelivery`, `completeDelivery` — только **своих** доставок |
| **Customer** | указан в поле `customer` доставки                             | `cancelDelivery` своей доставки                             |
| любой адрес  | —                                                             | чтение: `getDelivery`, `statusName`, `roles`, `canTransition` |

У адреса одна роль: повторный `grantRole` её заменяет.

### 4.3. Статусы и допустимые переходы

```solidity
enum Status { Created, Accepted, InTransit, Delivered, Cancelled }
//              0         1          2          3          4
```

| Статус      | Значение                                         |
| ----------- | ------------------------------------------------ |
| `Created`   | оператор зарегистрировал доставку по заказу      |
| `Accepted`  | назначен курьер, доставка принята в работу       |
| `InTransit` | курьер забрал заказ и везёт клиенту              |
| `Delivered` | заказ вручён, конечный статус                    |
| `Cancelled` | доставка отменена, конечный статус               |

```
             assignCourier            startDelivery            completeDelivery
  Created ─────────────────► Accepted ─────────────► InTransit ────────────────► Delivered
               (оператор)       │      (назнач. курьер)        (назнач. курьер)
     │                          │
     │       cancelDelivery     │
     └──────────────┬───────────┘
      (клиент или оператор)
                    ▼
                Cancelled          InTransit → Cancelled запрещён:
                                   после начала доставки отменить нельзя
```

Все допустимые переходы собраны в одной функции `canTransition(from, to)`.
Всё, чего в ней нет, запрещено:

| Из \ В        | Accepted | InTransit | Delivered | Cancelled |
| ------------- | :------: | :-------: | :-------: | :-------: |
| **Created**   |    ✅    |    ❌     |    ❌     |    ✅     |
| **Accepted**  |    —     |    ✅     |    ❌     |    ✅     |
| **InTransit** |    ❌    |     —     |    ✅     |    ❌     |
| **Delivered** |    ❌    |    ❌     |     —     |    ❌     |
| **Cancelled** |    ❌    |    ❌     |    ❌     |     —     |

### 4.4. Функции

| Функция                                    | Кто вызывает                           | Переход / результат                      | События                                    |
| ------------------------------------------ | -------------------------------------- | ---------------------------------------- | ------------------------------------------ |
| `constructor()`                            | тот, кто деплоит                       | становится `admin` и Operator            | `RoleGranted`                              |
| `grantRole(account, role)`                 | Admin                                  | выдаёт роль                              | `RoleGranted`                              |
| `revokeRole(account)`                      | Admin                                  | роль → `None`                            | `RoleRevoked`                              |
| `createDelivery(orderId, customer, price)` | Operator                               | → `Created`, возвращает `deliveryId`     | `DeliveryCreated`                          |
| `assignCourier(deliveryId, courier)`       | Operator (у `courier` должна быть роль Courier) | `Created → Accepted`            | `CourierAssigned`, `DeliveryStatusChanged` |
| `startDelivery(deliveryId)`                | назначенный курьер                     | `Accepted → InTransit`                   | `DeliveryStatusChanged`                    |
| `completeDelivery(deliveryId)`             | назначенный курьер                     | `InTransit → Delivered`                  | `DeliveryStatusChanged`                    |
| `cancelDelivery(deliveryId)`               | клиент этой доставки или Operator      | `Created/Accepted → Cancelled`           | `DeliveryStatusChanged`                    |
| `getDelivery(deliveryId)`                  | любой (`view`)                         | вся структура `Delivery`                 | —                                          |
| `statusName(deliveryId)`                   | любой (`view`)                         | статус строкой: `"Delivered"`            | —                                          |
| `canTransition(from, to)`                  | любой (`pure`)                         | `true` / `false`                         | —                                          |
| `roles(address)`, `admin()`, `deliveriesCount()`, `deliveryIdByOrderId(id)` | любой | геттеры public-переменных, их создаёт компилятор | — |

`statusName` сделана для удобства: в Remix enum показывается числом
(`3`), а она возвращает `Delivered`.

Все изменения статуса проходят через одну приватную функцию `_setStatus`.
Она меняет статус, обновляет `updatedAt` и отправляет `DeliveryStatusChanged`.
Поэтому сменить статус в обход события невозможно.

### 4.5. Модификаторы и порядок проверок

| Модификатор                  | Проверяет                                    | Ошибка                    |
| ---------------------------- | -------------------------------------------- | ------------------------- |
| `onlyAdmin`                  | вызывающий — `admin`                         | `NotAdmin`                |
| `onlyRole(role)`             | у вызывающего нужная роль                    | `MissingRole`             |
| `deliveryExists(id)`         | доставка с таким номером существует          | `DeliveryNotFound`        |
| `allowedTransition(id, to)`  | переход из текущего статуса в `to` разрешён  | `InvalidStatusTransition` |
| `onlyAssignedCourier(id)`    | вызывающий — назначенный курьер этой доставки | `NotAssignedCourier`     |

Модификатор выполняет проверку, а потом на месте `_;` выполняется тело
функции. Модификаторы срабатывают в том порядке, в котором записаны:

```solidity
function completeDelivery(uint256 deliveryId)
    external
    deliveryExists(deliveryId)                       // 1. доставка есть?
    allowedTransition(deliveryId, Status.Delivered)  // 2. переход разрешён?
    onlyAssignedCourier(deliveryId)                  // 3. это её курьер?
{
    _setStatus(deliveryId, Status.Delivered);
}
```

Статус проверяется **до** курьера. Поэтому `completeDelivery` для доставки
в `Created` (курьера ещё нет) вернёт понятную ошибку
`InvalidStatusTransition(0, 3)`, а не `NotAssignedCourier`.

### 4.6. События

| Событие                                                          | Когда                              |
| ---------------------------------------------------------------- | ---------------------------------- |
| `DeliveryCreated(deliveryId, orderId, customer, price)`          | создана доставка                   |
| `CourierAssigned(deliveryId, courier, operator)`                 | назначен курьер                    |
| `DeliveryStatusChanged(deliveryId, from, to, by)`                | любая смена статуса                |
| `RoleGranted(account, role, by)` / `RoleRevoked(account, role, by)` | выдана или отозвана роль        |

## 5. Обработка ошибок и запрещённые операции

| Ошибка                                  | Когда возникает                                       | Пример                                   |
| --------------------------------------- | ----------------------------------------------------- | ---------------------------------------- |
| `InvalidStatusTransition(from, to)`     | переход не разрешён таблицей из 4.3                    | `completeDelivery` в `Created` → `(0, 3)`; отмена в `InTransit` → `(2, 4)` |
| `MissingRole(caller, required)`         | нет нужной роли                                       | клиент вызывает `createDelivery`         |
| `NotAssignedCourier(caller, courier)`   | статус меняет не назначенный курьер                    | посторонний вызывает `startDelivery`     |
| `NotCustomerOrOperator(caller)`         | отменяет не клиент и не оператор                       | посторонний вызывает `cancelDelivery`    |
| `NotAdmin(caller)`                      | ролями управляет не admin                             | клиент вызывает `grantRole`              |
| `AccountIsNotCourier(account)`          | курьером назначают адрес без роли Courier             | `assignCourier(1, <адрес без роли>)`     |
| `DeliveryNotFound(deliveryId)`          | доставки с таким номером нет                          | `getDelivery(9)`                         |
| `OrderAlreadyRegistered(orderId, id)`   | на этот заказ доставка уже создана                    | второй `createDelivery(1001, …)`         |
| `ZeroAddress()` / `ZeroPrice()`         | пустой адрес или нулевая цена                         | `createDelivery(1, 0x000…0, 0)`          |
| `"Use revokeRole to remove a role"` (`require`) | `grantRole(адрес, 0)`                         | —                                        |

При любой из этих ошибок транзакция откатывается целиком: статус,
курьер и время не меняются, события не записываются.

Сценарий и все запрещённые операции заранее проверены автоматическим
прогоном (компилятор solc 0.8.24 и локальный тестовый блокчейн).
Все разрешённые шаги прошли, все запрещённые вернули ошибки из таблицы.

## 9. Ответы на возможные вопросы

**Зачем здесь блокчейн, если есть backend и БД?**
В обычной БД запись может изменить любой, у кого есть доступ к серверу:
администратор, разработчик, взломщик. Курьер мог бы «задним числом»
поставить «доставлено», оператор — удалить отмену. В контракте статус
меняется только по правилам из кода, каждое изменение подписано
конкретным аккаунтом и навсегда остаётся в истории. Это полезно, когда
участники (магазин, служба доставки, курьеры, клиенты) не обязаны доверять
друг другу, например при спорах «был ли заказ доставлен».

**Почему в блокчейн вынесена только часть логики?**
Запись в блокчейн дорогая (раздел 1, «Газ») и медленная, а все данные
в нём публичны. Поэтому каталог, корзина, расчёты и персональные данные
остаются в backend. В контракт попадает минимум: ссылка на заказ
(`orderId`), участники, статус и история.

**Почему Solidity, а не Java, как в прошлых работах?**
В задании требуется смарт-контракт в Remix IDE. Код контракта выполняет EVM,
и пишется он на Solidity (или Vyper). Java можно было бы использовать
только для клиента к контракту (библиотека web3j), но задание этого не
требует.

**Как контракт понимает, кто его вызвал? Можно ли подделать?**
Через `msg.sender`. Каждая транзакция подписана закрытым ключом аккаунта,
и сеть проверяет подпись. Отправить транзакцию от чужого адреса без его
ключа нельзя. Это аналог входа по паролю в Keycloak.

**Чем `require` отличается от пользовательских ошибок?**
Результат один — откат транзакции. `require` возвращает текстовую строку,
она дороже по газу и не несёт данных. Пользовательская ошибка
(`revert InvalidStatusTransition(from, to)`) дешевле и передаёт параметры.
В контракте используются оба способа, чтобы показать оба.

**Что происходит с данными, если транзакция отклонена?**
Ничего не меняется: EVM откатывает все изменения транзакции, события тоже
не сохраняются. В реальной сети отправитель всё равно платит за газ,
потраченный до ошибки. В Remix VM это тестовый ETH.

**Почему Created → Delivered нельзя, и где это проверяется?**
Таблица переходов — функция `canTransition`. Её вызывает модификатор
`allowedTransition` перед каждой сменой статуса. Из `Created` разрешены
только `Accepted` и `Cancelled`. Запрет срабатывает **до** проверки
курьера, поэтому ошибка — именно `InvalidStatusTransition(0, 3)`.

**Почему после начала доставки нельзя отменить?**
Из `InTransit` разрешён только переход в `Delivered`. Заказ уже у курьера
в пути, поэтому отмена в этот момент — уже возврат, а это отдельный процесс.

**Может ли один курьер завершить чужую доставку?**
Нет. `onlyAssignedCourier` сравнивает `msg.sender` с полем `courier`
конкретной доставки. Роли Courier недостаточно, нужно быть **назначенным**
курьером.

**Что значит `private` у `deliveries` — данные скрыты?**
Нет. `private` запрещает доступ только другим контрактам. Любой может
прочитать хранилище контракта напрямую с узла. Поэтому в контракте нет
ФИО, телефонов и адресов, только адреса аккаунтов и `orderId`.

**Можно ли исправить ошибку в развёрнутом контракте?**
Код изменить нельзя. Можно развернуть новую версию по новому адресу
(или заранее заложить прокси-контракт — паттерн upgradeable proxy).
Поэтому контракты тщательно тестируют до деплоя.

**Почему статус в logs и в `getDelivery` — число?**
`enum` хранится как `uint8`: `Created = 0`, `Accepted = 1`,
`InTransit = 2`, `Delivered = 3`, `Cancelled = 4`. Для удобства есть
`statusName`, которая возвращает строку.

**Зачем `deliveryIdByOrderId` и почему нумерация с 1?**
Чтобы один заказ из backend нельзя было зарегистрировать дважды.
В `mapping` для отсутствующего ключа возвращается `0`, поэтому номер `0`
зарезервирован под «нет доставки», и нумерация начинается с `1`.

**Почему `createDelivery` такая дорогая по газу?**
Она заполняет новые ячейки хранилища: 7 полей структуры (курьер пока
нулевой) и запись в `deliveryIdByOrderId`. Запись в пустую ячейку стоит
около 22 100 газа. Смена статуса пишет в уже заполненную ячейку, это
в несколько раз дешевле.

**Насколько точно `block.timestamp`?**
Это время блока, которое задаёт его создатель. Оно может отличаться от
реального на несколько секунд. Для истории доставки этого достаточно.
Для точного учёта времени по секундам полагаться на него нельзя.

**Как front-end или backend узнают об изменениях?**
Подписываются на события контракта (`DeliveryStatusChanged` и др.) через
узел Ethereum (библиотеки ethers.js, web3.js, web3j для Java). По
`indexed`-полям можно фильтровать: все события одной доставки или одного
курьера.

**Что будет, если admin потеряет ключ?**
Выдавать новые роли станет некому: в контракте нет механизма смены
администратора. В реальном проекте добавили бы функцию передачи прав
(`transferAdmin`) или мультиподпись. Для учебной работы это сознательное
упрощение.

**Как развернуть в настоящей тестовой сети?**
В Remix в поле **Environment** выбрать **Injected Provider - MetaMask**,
в MetaMask переключиться на тестовую сеть (например Sepolia) с тестовым
ETH из faucet и нажать **Deploy**. Контракт менять не нужно.

**Что можно улучшить?**
- Добавить оплату доставки (функция `payable`): клиент вносит ETH при
  создании, курьер получает его после `Delivered`, при отмене деньги
  возвращаются клиенту.
- Плотнее упаковать структуру (`status` рядом с `customer` в одной
  32-байтной ячейке), чтобы снизить стоимость `createDelivery`.
- Использовать готовый `AccessControl` из OpenZeppelin вместо своей системы ролей.
- Добавить функцию передачи прав администратора.
