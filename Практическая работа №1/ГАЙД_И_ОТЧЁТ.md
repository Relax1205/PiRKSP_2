# Практическая работа №1: гайд по запуску и материалы для отчёта

## Часть 1. Как запустить

Для `run.bat` нужен JDK (с компилятором `javac`). VS Code и IntelliJ IDEA могут обойтись без него.

### Вариант 0. VS Code (Extension Pack for Java)

Отдельный JDK не нужен: расширение компилирует код своим встроенным компилятором и запускает
программу через установленную Java.

1. Открыть папку `Практическая работа №1` через **File → Open Folder**.
2. Открыть `src/task1/Main.java` (или `task2`, `task3`) и нажать **Run** над методом `main`
   либо ▷ в правом верхнем углу.
3. Вывод появится во вкладке **Terminal**. Там же вводятся числа для задания 2.
   Задание 1 после строки «Доступно ядер» молчит ~15–50 секунд (идёт последовательный вариант),
   затем выводится таблица.
4. Аргументы (`MAX 10000`, `20` и т.п.): **Run and Debug** (Ctrl+Shift+D) → «create a launch.json file»
   → в нужной конфигурации добавить `"args": "MAX 10000"`.

### Вариант А. IntelliJ IDEA

1. **File → Open** → выбрать папку `Практическая работа №1`.
2. ПКМ по папке `src` → **Mark Directory as → Sources Root** (папка станет синей).
3. **File → Project Structure → Project → SDK**. Если там пусто:
   **Add SDK → Download JDK** → Eclipse Temurin, версия 17 (или 8) → Download.
   Там же поле **Language level**: оставить по умолчанию.
4. Открыть нужный файл и нажать зелёный треугольник рядом с `public static void main`:
   - `src/task1/Main.java` — задание 1 (работает ~15–50 секунд: последовательный вариант медленный, это нормально);
   - `src/task2/Main.java` — задание 2 (числа вводятся в консоль внизу IDEA);
   - `src/task3/Main.java` — задание 3.
5. Передать аргументы (необязательно): **Run → Edit Configurations → Program arguments**.
   - задание 1: `SUM 10000`, `MAX 10000` или `MIN 10000` (операция и размер массива);
   - задание 3: `20` (количество файлов).

Если в консоли вместо русских букв «кракозябры»: **Settings → Editor → File Encodings**, везде
поставить UTF-8. Затем в **Edit Configurations → VM options** добавить `-Dfile.encoding=UTF-8`.

### Вариант Б. Командная строка

1. Установить **JDK** (не JRE с java.com: в JRE нет `javac`), например Eclipse Temurin 17
   с adoptium.net. При установке отметить
   «Set JAVA_HOME» и «Add to PATH».
2. Открыть **новое** окно терминала и проверить: `javac -version`.
3. В папке проекта выполнить:
   ```
   run.bat 1 SUM 10000
   run.bat 2
   run.bat 3 20
   ```

### Что вводить в задании 2 для скриншота

Вводить строки **быстро, одну за другой, не дожидаясь ответов**. Если ждать ответ на каждый
запрос, асинхронность на скриншоте не видна: всё выглядит как обычная последовательная программа.
```
5
12
-7
abc
9999999999999
status
exit
```
На скриншоте будет видно:
- запросы принимаются сразу, а результаты приходят позже и в другом порядке;
- для `abc` выводится ошибка ввода;
- для `9999999999999` квадрат не помещается в `long`, и выводится ошибка вычисления из `Future`;
- после `exit` программа дожидается незавершённых запросов.

## Часть 2. Материалы для отчёта

**Структура отчёта:** титульный лист → цель → задание → ход работы (по каждому заданию:
описание решения, листинг ключевого кода, скриншот результата) → выводы.

> Числа в таблице задания 1 взяты из запуска `run.bat 1 SUM 10000` на этом компьютере (16 ядер).
> При повторном запуске они немного изменятся: скриншот и таблица должны быть из одного запуска.

### Цель работы

Развить навыки работы с многопоточностью и параллельными вычислениями в Java:
- реализовать обработку массива последовательно, с помощью потоков `Thread` и фреймворка ForkJoin;
- освоить `Thread`, `Future`, `ExecutorService` и `ForkJoinPool`;
- создать асинхронную программу на основе `Future`;
- спроектировать многопоточную систему с учётом потокобезопасности.

### Задание 1. Обработка массива тремя способами

**Постановка.** Найти сумму (максимум, минимум) элементов массива из 10 000 целых чисел
тремя способами: последовательно, с использованием многопоточности и с использованием ForkJoin.
Обработка каждого элемента сопровождается задержкой 1 мс. Сравнить время выполнения
и объём используемой памяти.

**Описание решения.**
- `Operation`: перечисление операций. Каждая задаётся нейтральным элементом и ассоциативной
  функцией объединения, поэтому частичные результаты из разных потоков можно объединять
  в любом порядке.
- `ArrayProcessor.sequential`: проход по массиву в одном цикле.
- `ArrayProcessor.multithreaded`: массив делится на N частей (N равно числу ядер процессора),
  для каждой части создаётся отдельный `Thread`. Каждый поток записывает результат в свою ячейку
  массива `results`, а основной поток читает результаты после `join()`. Потоки не пишут в общие
  данные, поэтому синхронизация не требуется.
- `ArrayProcessor.RangeTask`: наследник `RecursiveTask<Long>`. Если отрезок длиннее 250
  элементов, он делится пополам: левая половина отправляется в пул через `fork()`, правая
  считается в текущем потоке через `compute()`, затем результаты объединяются после `join()`.
  Задача запускается через `ForkJoinPool.invoke()`.
- Время измеряется через `System.nanoTime()`. Память оценивается как разница
  `totalMemory() - freeMemory()` до и после вычисления (перед замером вызывается `System.gc()`).

**Результаты** (операция SUM, 10 000 элементов, 16 ядер):

| Способ                   | Результат | Время, мс | Память, КБ |
|--------------------------|----------:|----------:|-----------:|
| Последовательно          |   4978832 |     16664 |        327 |
| Многопоточно (16 Thread) |   4978832 |       955 |         24 |
| ForkJoinPool (16)        |   4978832 |      1266 |        672 |

Ускорение относительно последовательного варианта: Thread в 17,45 раза, ForkJoin в 13,16 раза.

**Вывод по заданию 1.**
Все три способа дали одинаковый результат (4978832), значит параллельные реализации корректны.
Многопоточная обработка оказалась в 17,45 раза быстрее последовательной, ForkJoin в 13,16 раза.
Ускорение близко к числу ядер (16) и даже немного превышает его, потому что задача не нагружает
процессор, а в основном ждёт (`Thread.sleep`): спящие потоки не конкурируют за ядра. Кроме того,
последовательный вариант занял 16,7 с вместо ожидаемых 10 с, так как в Windows `sleep(1)`
фактически длится дольше 1 мс. Ручное разбиение на `Thread` оказалось быстрее ForkJoin: при
одинаковом числе потоков ForkJoin дополнительно тратит время на рекурсивное создание подзадач
и распределение их по очередям. ForkJoin также потребовал больше всего памяти (672 КБ): она уходит
на объекты подзадач `RangeTask` и внутренние очереди пула. Вариант с `Thread` создаёт только
16 объектов потоков и массив результатов, поэтому расходует меньше всего памяти. Преимущество ForkJoin в другом: код не
зависит от ручного разбиения массива, пул сам распределяет подзадачи между потоками (work
stealing) и лучше подходит для рекурсивных алгоритмов. Замер памяти через `Runtime`
приблизительный, так как на него влияет работа сборщика мусора.

### Задание 2. Асинхронная обработка запросов с помощью Future

**Постановка.** Пользователь вводит число, программа возводит его в квадрат с задержкой
от 1 до 5 секунд, используя `Future`. Пользователь может вводить новые запросы,
не дожидаясь результата предыдущих.

**Описание решения.**
- Для каждого введённого числа в `ExecutorService` (`Executors.newCachedThreadPool()`)
  отправляется задача `SquareTask implements Callable<Long>`. Метод `submit()` сразу возвращает
  `Future<Long>`, поэтому основной поток не блокируется и продолжает читать ввод.
- Запросы (номер, число, `Future`) хранятся в потокобезопасном списке `CopyOnWriteArrayList`,
  так как в него пишет основной поток, а читает и удаляет фоновый.
- Фоновый поток `ResultPrinter` каждые 100 мс проверяет `future.isDone()` и выводит готовые
  результаты через `future.get()`. Для завершённой задачи этот вызов не блокирует поток.
- Исключение внутри задачи (переполнение в `Math.multiplyExact`) не теряется: оно передаётся
  в основной код как `ExecutionException` при вызове `get()`.
- По команде `exit` пул закрывается через `shutdown()`, программа ждёт окончания задач
  (`awaitTermination`) и завершает фоновый поток. Флаг завершения помечен `volatile`.

**Результаты:** скриншот сессии, где запросы принимаются мгновенно, а ответы приходят позже
и в порядке готовности, а не в порядке ввода.

**Вывод по заданию 2.**
Интерфейс `Future` позволяет отделить запуск долгой операции от получения её результата:
программа остаётся отзывчивой и принимает новые запросы, пока предыдущие вычисляются в пуле
потоков. Результаты приходят в порядке готовности, а не в порядке ввода, что подтверждает
параллельное выполнение. Проверка `isDone()` позволяет получать результат без блокировки, а
`get()` передаёт в вызывающий код как значение, так и исключение, возникшее в другом потоке.
Для обмена данными между потоками использованы потокобезопасная коллекция и `volatile`-флаг.

### Задание 3. Система обработки файлов

**Постановка.**
- Генератор создаёт файлы со случайным типом (XML, JSON, XLS) и размером (10–100)
  с задержкой 100–1000 мс.
- Файлы помещаются в очередь вместимостью 5 элементов.
- Обработчики забирают из очереди файлы только своего типа; время обработки равно
  размеру файла × 7 мс.

**Описание решения.**
- `File`: неизменяемый класс (все поля `final`), поэтому его безопасно передавать между потоками.
- `FileQueue`: собственная потокобезопасная ограниченная очередь. Всё состояние защищено одной
  блокировкой `ReentrantLock` с двумя условиями:
  - `put()` ждёт на условии `notFull`, пока очередь заполнена (5 файлов);
  - `take(type)` ищет файл нужного типа и, если его нет, ждёт на условии `fileAdded`;
  - после добавления файла будятся все обработчики (`signalAll`), каждый проверяет, есть ли файл
    его типа; после извлечения файла будится генератор (`signal`).
  - Ожидание в цикле `while` защищает от ложных пробуждений.
- `FileGenerator`: поток, создающий файлы и помещающий их в очередь.
- `FileProcessor`: по одному потоку на каждый тип файлов.
- Корректное завершение: после окончания генерации вызывается `queue.close()`. Обработчики
  дорабатывают оставшиеся файлы своего типа, затем `take()` возвращает `null`, и поток
  завершается. Основной поток ждёт все потоки через `join()`.
- В лог выводятся время, имя потока и событие, что позволяет проследить параллельную работу.

**Результаты:** скриншот лога: создание файлов, одновременная обработка файлов разных
типов, итоговая статистика по обработчикам.

**Вывод по заданию 3.**
Реализована многопоточная система «производитель — очередь — потребители». Ограниченная очередь
выравнивает скорость генерации и обработки: если обработчики не успевают, генератор
приостанавливается, пока не освободится место. Разделение обработчиков по типам позволяет
обрабатывать файлы разных типов одновременно. Потокобезопасность обеспечена одной блокировкой
`ReentrantLock` на всё состояние очереди и условиями `Condition` для ожидания без активного
опроса (потоки не расходуют процессор, пока ждут). Неизменяемость объекта `File` исключает гонки
данных при передаче между потоками. Механизм закрытия очереди гарантирует, что все созданные
файлы будут обработаны, а потоки завершатся без принудительного прерывания.

### Общий вывод

В ходе работы изучены основные средства многопоточного программирования в Java:
- класс `Thread`, ожидание завершения потока через `join()`;
- фреймворк ForkJoin (`ForkJoinPool`, `RecursiveTask`) для рекурсивных параллельных вычислений;
- пул потоков `ExecutorService` и интерфейс `Future` для асинхронного получения результатов;
- средства синхронизации `ReentrantLock` и `Condition`, потокобезопасные коллекции,
  модификатор `volatile`.

Эксперимент показал, что распараллеливание задач, связанных с ожиданием, даёт кратное ускорение.
Выбор способа зависит от задачи: `Thread` даёт полный контроль, ForkJoin удобен для рекурсивного
деления данных, а `Future` подходит для асинхронных операций, не блокирующих основной поток.
При проектировании многопоточных систем важно исключать гонки данных. Для этого применяются
неизменяемые объекты, блокировки и потокобезопасные структуры данных, а также продумывается
корректное завершение потоков.
